## 1. Fix set identity `me4` / `me04`

### Cosa ho trovato

**Non è un caso isolato — sono 26 gruppi di collisione in Pokémon EN** (query `setIdentityKey`):

| Pattern | Esempi |
|---|---|
| zero-padding | `me01`/`me1`, `me02`/`me2`, … `me05`/`me5`, `sv01`/`sv1` … `sv09`/`sv9` |
| notazione point | `sv03.5`/`sv3pt5`, `sv04.5`/`sv4pt5`, `sv06.5`/`sv6pt5`, `sv08.5`/`sv8pt5`, `swsh12.5`/`swsh12pt5`, `sm3.5`/`sm35`, `swsh4.5`/`swsh45`, `swsh4.5sv`/`swsh45sv`, `swsh12.5gg`/`swsh12pt5gg` |

**Provenienza:** **20.479 righe `pokemon:ptcg:*`** (namespace pokemontcg.io), create **2026-06-14 → 2026-08-11** da `sync-pokemon-ptcg.js` (backfill illustrator, workflow **manuale**). Usa lo spelling non-padded/non-dotted (`sv1`, `sm35`). Il sync schedulato (`sync-cards.js`, TCGdex) usa lo spelling padded/dotted (`sv01`, `sm3.5`) — **due sorgenti, due convenzioni, righe carta separate** (`cards.id` diverso: `pokemon:ptcg:sv1-1` vs `pokemon:tcgdex:sv01-1:en`).

### Verifica riferimenti (FK + user data)

**FK verso `cards.id`** (tutti `ON DELETE CASCADE`, tranne `canonical_cards.primary_image_card_id` = `SET NULL`):
`card_prices`, `card_image_cache`, `hot_picks`, `market_observations`, `market_valuations`, `canonical_cards`.

**Riferimenti NON-FK (text, app-level) — il rischio vero:** `collection.card_api_id`, `watchlist.card_api_id`, `alerts.card_api_id`. **Verificato: utenti reali hanno lo stesso oggetto sotto entrambi gli spelling** (es. `pokemon:ptcg:me2-13` E `pokemon:tcgdex:me02-013:en` nella watchlist dello stesso utente per "Mega Charizard X ex"). Un DELETE/merge naïve orfanerebbe le loro entry.

**19.216 righe `ptcg` hanno `illustrator`** (era lo scopo del backfill) — non si possono cancellare senza prima verificare che il gemello TCGdex abbia lo stesso dato.

### Cosa ho fatto in 2.1 (sicuro, non distruttivo)

1. **`setIdentityKey(raw)`** — nuova funzione in `scripts/lib/catalog/normalize-set-code.js`. Collassa zero-padding + `pt`↔`.`, **senza toccare `normalizeSetCode`** (che resta stabile per gap/diff/card-number). 5 test di equivalenza + 4 anti-regressione (`sv1` ≠ `sv10`, `sv08` ≠ `sv08.5`, …).
2. **Report completo** delle 26 collisioni (sopra) + analisi FK.

### Cosa NON ho fatto (e perché è giusto così)

**Il dedup vero è una migration Fase 1.x, non 2.1**: ~20k righe, re-pointing di `card_api_id` in `collection`/`watchlist`/`alerts`, merge del campo `illustrator`, gestione `canonical_card_id`. Non è "breve".

**Cruciale: NON impatta il valuation layer.** Verificato con query diretta:
```
osservazioni market_observations sui set duplicati non-padded (me1,sv1,sv3pt5,…) = 0
```
`ingest-market-tcgcsv.js` risolve i set contro la lista **autoritativa TCGdex** (`buildPokemonSetIndex`) → attribuisce sempre allo spelling canonico. Le righe `ptcg` duplicate sono orfane in `cards`, senza osservazioni né valutazioni. **Il Portfolio non le vedrà come "valued".**

### Piano tecnico Fase 1.x (per dopo)

`docs/plans/` → nuova migration `dedup_pokemon_ptcg_set_ids`:
1. Tabella di mapping reversibile `set_id_dedup_map (dup_id, canon_id, reason)`.
2. Per ogni set collidente: `canon` = spelling TCGdex (`sv08.5`, `me04`). Per ogni carta `ptcg`, trovare il gemello TCGdex via `setIdentityKey` + `card_number_norm`.
3. **Merge `illustrator`/`evolves_from`** dal `ptcg` al gemello TCGdex se mancante.
4. **Re-point** `collection`/`watchlist`/`alerts`/`card_submissions.card_api_id` (`ptcg` → gemello).
5. Re-point o lasciar cadere in CASCADE `card_prices`/`card_image_cache`/`hot_picks` (dati vecchi, ri-derivabili).
6. `delete from cards where id = <ptcg dup>` (CASCADE pulisce il resto).
7. **Guard**: `sync-pokemon-ptcg.js` → o riscrive con lo spelling canonico, o si retira (pokemontcg.io è morta all'85%). Aggiungere a `catalog-freshness` un KPI "identity-key collisions" ≠ 0.
8. Migration idempotente + test anti-regressione (ri-eseguire = no-op).

## 2. Valuation stress test (campione rappresentativo)

Motore **non modificato prima** del test (F3/F4 applicati dopo, come fix autorizzati).

### Outlier / casi fuorvianti trovati (Fase 2, PRIMA dei fix)

| # | Caso | Esempio | Perché fuorviante |
|---|---|---|---|
| A | **Blend di varianti stesso numero** | `onepiece:optcg:OP01-003` → **€415**, range [€88 – €743] | 2 prodotti TCGCSV ("OP01-003" base + "OP01-003 Alternate Art") attribuiti alla stessa carta DB. €415 non corrisponde a nessun prodotto reale. |
| B | **Blend di finish (Pokémon)** | `sv08.5-059` → est €0.44 ma osservazioni Holofoil €0.44 / €3.94 / **€68.64** (3 prodotti "059/131": base, Poké Ball pattern, Master Ball pattern) | Finish diversi = prodotti diversi. Mescolarli = valore che non esiste. |
| C | **Range collassato** | `OP09-118` → n=3, ma `observed_low = median = high = €22.61` mentre le osservazioni vanno da €22 a **€25.906** | `observed_*` calcolato su un pool deduplicato a 1 elemento → range a larghezza zero che *mente*. |
| D | **Placeholder TCGplayer** | `onepiece:tcgcsv:710857` → **€21.589**, `medium` | Un unico annuncio a €29.994,99 (`low==mid==high`), nessun mercato reale. |
| E | **Sub-cent** | `OP07-025` → €0.01 | Non sbagliato ma da etichettare "bulk". |
| F | **Valore alto senza corroborazione** | `onepiece:tcgcsv:712117` → **€6.908**, n=1, `medium` | Un singolo snapshot TCGplayer da migliaia di euro non merita `medium`. |

### Fix applicati (targeted, non redesign)

- **A** → `ingest`: match per-numero salta i prodotti-variante One Piece (`detectPrintVariant` sul nome).
- **A+B** → `ingest`: `collapseByNumberDuplicates` — per i match per-numero, tiene **solo la stampa più economica** per `(card_id, sub_type)` (= la base).
- **B** → `valuation`: `primarySubtypeObservations` — il valore headline usa **un solo sub_type** (il più osservato, tie-break `Normal` > `Holofoil` > …), niente blend.
- **C** → `valuation`: `observed_low/high` da `dedupeBySourceSubtypeDay` (dispersione reale fra fonti/giorni), non dal pool ridotto. Se c'è 1 solo prezzo distinto → `low == median == high` è corretto (una sola osservazione).
- **D** → `ingest` + `valuation`: `isPlaceholderObservation` — scarta `low==mid==high && price >= €1000`.
- **F** → `valuation`: `estimated_value >= €2000 && n_obs < 2 && n_sources < 2` → confidence cap `low`.

### Risultato post-fix (re-ingest pulito + re-compute)

- `low` fuorvianti: **509 → 0**. `low` legittime (chase non corroborate): **3**.
- Phantom €21k: **eliminato**. Max valore ora €6.908 (OP-17 alt-art reale, ora `low` per il cap F).

- **100% dei valori ∈ [observed_low, observed_high]**.

## 4. Caveat per il team Portfolio (Fase 3)

Il layer è affidabile **come architettura e semantica**, ma **magro come dati** (per ora):

1. **Ogni valutazione è `n_observations = 1, n_sources = 1`** — 1 giorno, 1 fonte (TCGCSV/TCGplayer market). Corretto e onesto, ma:
   - `confidence` è al massimo `medium` — **non progettare uno stato UI "high"** finché non c'è una 2ª fonte (Fase 2.2).
   - `trend_7d_pct` / `trend_30d_pct` sono **`null` per tutti** — servono ~2 settimane di snapshot giornalieri. Il grafico storico del Portfolio deve gestire "storia insufficiente" con grazia.
   - `observed_low == median == high` per la maggior parte (1 osservazione) — mostrare "€X" senza range finché n=1, il range compare quando i dati crescono.
2. **Mostrare sempre `confidence` + `computed_at`/"as of"** — mai un numero nudo.
3. **Copertura ~50% delle carte priorità**: SV04.5→SV10.5 + ME01→ME06 (Pokémon EN), OP-01→OP-17 + starter/RE (One Piece). Le carte fuori copertura hanno **0 righe in `market_valuations`** → il Portfolio deve avere una sezione esplicita "carte senza valutazione affidabile" (`confidence='none'` o riga assente).
4. **JP: nessuna valutazione** (fonte EN-only). Le posizioni JP del Portfolio mostrano "valutazione non disponibile per questa lingua".
5. **I set `ptcg` duplicati** (`me4`, `sv1`, …): 0 valutazioni. Se il Portfolio incontra una `collection.card_api_id` che punta a uno di quelli → nessun match in `market_valuations`. Mitigazione temporanea: risolvere via `setIdentityKey` lato lettura Portfolio, oppure aspettare il dedup Fase 1.x.
